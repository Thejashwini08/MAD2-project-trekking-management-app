# Trekking Management Application (TMA) — MAD 2

A trek booking and coordination platform built for adventure organizations, connecting three kinds of users — the **Admin**, **Trek Staff**, and **Trekkers (Users)** — around a shared pool of treks and bookings.

The backend is a Flask REST API; the frontend is a Vue 3 single-page app loaded straight from CDN script tags (no bundler/build step required); background work (reminder emails, monthly reports, CSV exports) runs through Celery with Redis as the broker and result backend, and Redis also caches the trek-listing endpoint.

---

## 1. What this app does

- **Admin** logs in with a pre-seeded account, creates and edits treks, hires Trek Staff, assigns staff to specific treks, and can blacklist/unblacklist any Staff or Trekker account. The admin dashboard shows live counts of treks, staff, trekkers, and bookings.
- **Trek Staff** accounts are created only by the Admin (no public sign-up for staff). Each staff member sees only the treks assigned to them, can update available slots and the trek's status, and can view everyone currently booked on their treks.
- **Trekkers (Users)** self-register, browse and filter open treks, book a slot, cancel a booking (which frees the slot back up), and review their full trekking history. From the history page they can also kick off an asynchronous export of that history to CSV.

A trek moves through a simple lifecycle — `Pending → Approved → Open → Closed/Completed` — and a booking follows `Booked → Cancelled/Completed`. Marking a trek `Completed` automatically flips every still-`Booked` booking on it to `Completed` too, so trekkers never have to update their own booking status by hand.

## 3. Running it locally

You'll need four terminals open at once: Redis, the Flask API, the Celery worker, and (optionally) Celery beat for the scheduled jobs.

```bash
#WSL 1) Redis (broker + result backend + cache) 
redis-server

#Power shell 2) Flask API
cd backend
pip install -r requirements.txt
python app.py                       # http://127.0.0.1:5000

#cmd 3) Celery worker — handles the CSV export job
cd backend
celery -A celery_app.celery worker --loglevel=info --pool=solo
#                                              ^^^^^^^^^^^^^^^ required on Windows,
# the default "prefork" pool crashes there with a billiard/WinError 6 error.

#cmd 4) Celery beat — fires the reminder + monthly report jobs on schedule
cd backend
celery -A celery_app.celery beat --loglevel=info
```

The frontend needs **no separate server or build step** — `index.html` is served directly by Flask's static file handling, so once step 2 is running, just open `http://127.0.0.1:5000` in a browser.

The database (`backend/trekking.db`) is created automatically on first run, and the single Admin account is seeded programmatically the first time the app starts — there is no admin sign-up page.

**Default admin login:** `admin@trek.com` / `admin123`

## 4. Background jobs

| Job | Trigger | What it does |
|---|---|---|
| `send_daily_reminders` | Celery beat, daily | Emails every trekker with an active booking on a trek starting within the next few days; each booking is only reminded once (`reminder_sent` flag on `Booking`) |
| `generate_monthly_report` | Celery beat, 1st of each month | Builds an HTML summary (treks run, bookings, most-booked treks), saves it to `backend/reports/` as `monthly_report_<YYYY>_<MM>.html`, and emails it to the admin |
| `export_user_bookings_csv` | User clicks "Export as CSV" on their history page | Runs in the background via Celery, writes a CSV to `backend/exports/` as `booking_history_user_<user_id>_<uuid>.csv`, and the frontend polls for completion before offering the file for download |

## 5. Caching

`GET /api/treks` (the trekker-facing "browse open treks" endpoint) is cached in Redis per unique combination of filters for 60 seconds, and the cache is proactively cleared whenever a trek is created, edited, booked, or cancelled — so a stale listing never lingers longer than the TTL, and any change is reflected immediately.

## 6. Notable business rules enforced server-side

- A trekker cannot book the same trek twice, and cannot re-book it even after it's marked `Completed` (only a `Cancelled` booking can be re-booked).
- Booking is only allowed while a trek's status is exactly `Open` and it still has free slots — this is checked on the server, not just hidden in the UI.
- Only the staff member a trek is actually assigned to can view or update that trek.
- Blacklisting a Staff or Trekker account immediately blocks that account from logging in again.
